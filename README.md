# Rayhab Movement Clinic

Website for Rayhab Movement Clinic, Beirut. Specialised scoliosis rehabilitation,
Schroth-based, plus sports rehabilitation, joint training and mobility, and general
physiotherapy.

Static site: plain HTML, CSS custom properties and vanilla JavaScript. No build
step and no framework. Open `site/index.html` or serve the `site/` directory.

- **Production (planned):** <https://dr-rayhab.com>, on a VPS behind Nginx, with
  a booking API built by a separate backend developer. See
  [Launch and backend handoff](#launch-and-backend-handoff).
- **Staging:** <https://ronimassoud.github.io/rayhab-movement-clinic/>
- **Repository:** <https://github.com/ronimassoud/rayhab-movement-clinic>
- **Design canvas:** [Rayhab UI on Claude Design](https://claude.ai/design/p/c0ba2874-187e-4463-b422-73d41cc99cb9?file=Rayhab+UI.dc.html)
  (the source the site was built from, kept byte-exact at `Rayhab UI.dc.html`)

> **Not ready for launch.** The booking and contact forms need the backend
> described below, and the items under [Before launch](#before-launch) and the
> [launch blockers](#launch-blockers) are open. The GitHub Pages staging copy is
> public but marked noindex on every page, so search engines do not index it;
> it still exposes clinical photographs and articles awaiting clinical review
> to anyone with the link.

## Deployment

Pushing to `main` publishes the **staging** copy of `site/` to GitHub Pages via
`.github/workflows/pages.yml`. In order, it rebuilds the stylesheet, versions
asset URLs (`content/stamp.py`), writes `sitemap.xml` from the indexable pages
(`content/sitemap.py`), runs `.github/scripts/check_links.py`, and finally marks
every page noindex (`content/staging_noindex.py`) so the mirror never competes
with production in search.

`check_links.py` fails the deploy on a broken internal link or `#anchor`, a page
missing the motion or menu markup, an indexable page without its title,
description, production canonical or share image, or a sitemap that differs
from the indexable pages.

Canonical URLs, the sitemap, `robots.txt` and social share links all use the
production origin in `content/site_config.py` (`SITE_URL`). Production hosting
is described in [Launch and backend handoff](#launch-and-backend-handoff); it
must not run the staging noindex step.

## Running it

```bash
python -m http.server 4488 --directory site
```

Then open <http://localhost:4488>. A `.claude/launch.json` config is included for
the editor's preview pane.

The pages are static and the compiled stylesheet is committed, so viewing the
site needs nothing but that. Changing the styles needs Node:

```bash
npm install
```

```bash
npm run dev
```

`npm run dev` rebuilds `site/assets/css/rayhab.css` on every save; `npm run build`
does one minified build. The deploy workflow runs the build again before it
publishes, so the live stylesheet cannot lag the source.

Every stylesheet and script URL carries a content hash (`rayhab.css?v=80d295bc`),
so a browser can never pair a new page with a cached old file. The generators add it
as they write; after a stylesheet build, or an edit to a hand-written page or a
script, restamp everything:

```bash
python content/stamp.py
```

The deploy workflow runs the same step after `npm run build`.

## Regenerating content

The 49 articles, the 5 non-scoliosis education hubs and the 3 supporting service
pages are generated, not hand-written as HTML. Prose lives in JSON so it can be
edited without touching 72 files.

```bash
cd content
python build_articles.py     # 25 scoliosis articles + 4 pillar and 3 route index pages + the library
python build_topics.py       # 5 education hubs + 24 articles
python build_services.py     # 3 supporting service pages
```

Every generated page passes through the same post-processing as the
hand-written ones: `motion_tags.inject()`, `navcards.inject_navcards()`,
`seo_tags.inject_seo()` (canonical, self-hosted font preloads, the API meta tag
and the share tags) and `stamp.py`. After editing a hand-written page's head,
run `seo_tags.inject_seo()` over it, or rebuild and let CI catch omissions.

| Script | What it does | When |
|---|---|---|
| `content/sitemap.py` | Writes `site/sitemap.xml` from the indexable pages | CI, or by hand |
| `content/staging_noindex.py` | Adds noindex to every page | Staging CI only |
| `content/og_image.py` | Draws the 1200x630 share image from the brand assets | By hand, when they change |
| `content/site_config.py` | Production origin, API base, share image | Edit, then rebuild |

`wire.py` and `wire_services.py` are **one-off patchers that have already
run**. They are kept for the record, not for the build. Do not run them:
`wire.py` would reintroduce the `.slot-txt` placeholder notes that were
deliberately moved into comments, and append sitemap URLs on `dr-rayhab.com`,
which is not the domain this site is served from. The three pages it
produced, the audience routes under `scoliosis/`, are maintained by hand.

`build_articles.py` and `build_topics.py` derive each article's reading time from
its own word count, so the label cannot drift from the text. The scoliosis library
carries the Schroth byline; the five general hubs carry the credential that
actually applies to them, which is set per topic. All three builders wrap trailing
navigational arrows for the hover animation; data arrows such as `29° → 20°`
are deliberately left alone.

## Brand assets

`rayhab-logo.png` is the 2172x724 master and is not referenced by any page.
The two assets that ship are derived from it:

- `favicon.png` (32px) and `apple-touch-icon.png` (180px) carry the R

  illegible smear; one letterform is the only thing that reads at that size.
- `rayhab-wordmark.png` is the CSS mask behind `.wordmark`. It is 448px wide
  for a 112px render, which covers 4x device pixel ratio, and its colour

Regenerate both from the master rather than editing them in place.

## The scoliosis library

Twenty-four articles, one list, eight ways in. `library.html` is the whole
set; the four topic views and the three situation views are the same list
filtered, and every one of them renders from `render_index()` in
`build_articles.py` with a different subset.

They were separate pages over overlapping subsets before, which is why the
hub felt like it offered four competing routes into one shelf: a parent who
opened "Parents of adolescents" and then "Pillar 01" met the same layout
twice with nothing saying the two were one library. Seventeen of the
twenty-four appeared on more than one page with no way to tell.

Every view now carries the same bar of chips, so the relationship is
visible and switching is one click. The bar is plain links, so it works
without JavaScript; `ui.js` only nudges the horizontal track on a phone
so the active chip is not off-screen.

Adding a view means adding an entry to `routes` in `articles.json` and a
label in `VIEW_LABEL`. Nothing else changes.

## Motion

GSAP 3.13 with ScrollTrigger drives all movement, from one file,
`site/assets/js/motion.js`, on every page except `book.html`. SplitText is
loaded on the home page only, where a headline is split.

| Scene | What it does |
|---|---|
| reveals | sections rise as they enter, driven by `data-reveal` in the markup |
| hero | the floating cards and the photo fan settle into place |
| headline | the home headline rises line by line |
| tilt | the three quotes close from a wider fan as they scroll in |
| nav | the floating pill steps aside going down and returns going up |
| line art | the Cobb-angle drawing in the closing band draws with the scroll |
| process | the rule above each of the six stages fills in turn |
| count | the measured angles count to their result |
| reading | progress across an article's body |
| cases | where you are in the five case studies |

The markup API for reveals, so the Python generators can emit them without the
script carrying a list of selectors:

```
data-reveal                 fade and rise this element
data-reveal="children"      stagger its direct children instead
data-reveal-stagger="60"    ms between children (default 70)
data-reveal-delay="120"     ms before the group starts
data-reveal-y="8"           px of travel (default 14)
```

Three rules hold for every scene.

- **Nothing is required.** An inline script in the head adds `.js-motion` to
  `<html>`, which is the only thing that hides a reveal target, and arms a
  2600 ms failsafe that removes it again. `motion.js` disarms it when it takes
  over. If GSAP is blocked or never arrives, `ui.js` drops the class as soon as
  the page has loaded. Either way the page is simply visible.
- **Reduced motion is checked in the script.** The stylesheet's global
  `prefers-reduced-motion` switch stops CSS transitions but cannot reach the
  inline styles GSAP writes each frame. Every scene is therefore registered
  inside `gsap.matchMedia()` on that query, and the head script never adds the
  class when the preference is set.
- **No scroll hijacking.** `normalizeScroll` and ScrollSmoother are never used.
  Either would break the fixed nav, the fixed booking bar and scrolling inside
  the booking dialog.

`content/motion_tags.py` injects the head script and the script tags into all
63 generated pages and the 8 hand-written ones, and `.github/scripts/check_links.py`
fails the deploy if any page but `book.html` is missing them.

## GSAP

Self-hosted in `site/assets/js/vendor/`, pinned to 3.13.0 in `package.json`, with
hashes in `vendor/README.md`. It is not loaded from a CDN: that would add a
second origin to every first visit, and on a health site it would hand a third
party the visitor's address together with the page they were reading.

Cost: about 46 KB gzipped for the core and ScrollTrigger on every page, plus
3.5 KB for SplitText on the home page. All three load with `defer`.

Things to keep when adding a scene:

- Use `gsap.matchMedia()` and the site's own breakpoints (700, 1060).
- Scrubbed and pinned work is desktop only.
- `document.fonts.ready` already triggers a refresh. Bricolage loads with
  `display=swap`, and the swap moves every heading.
- Triggers are disabled while the booking dialog is open, because
  `html.modal-open` changes the scroller's height.
- Animate `--tilt`, not `rotation`, on a tilted card. The lean is the CSS
  `rotate` property, which leaves `transform` free.

## Design system

Rayhab's own palette and typefaces, arranged on the structure of the Tomorro
reference system: a 1200px column on full-bleed bands, a floating pill
navigation, editorial display type, flat cards, and elevation held back for the
few things that float.

**Source.** `src/css/` compiles through Tailwind v4 into one file.

| File | Holds |
|---|---|
| `theme.css` | the tokens, in Tailwind's `@theme`. Colour, type scale, radius, breakpoints, shadow |
| `base.css` | document defaults, focus, runtime variables, the reduced-motion switch |
| `components.css` | surfaces, type classes, navigation, buttons, cards, media, tilt, closing band, footer |
| `site.css` | page composition and interaction |
| `mobile.css` | the phone compositions, which are separate layouts rather than reflowed desktop |
| `booking.css` | the booking flow and its dialog |

Tailwind's default palette, fonts, radii and shadows are cleared in `theme.css`,
so only brand values exist as utilities. Utilities in the markup handle one-off
spacing, width and colour; anything repeated is a named component, because 63
pages are generated and there is no component framework to hold fifteen
utilities in one place.

**Tokens.**

| | |
|---|---|
| Surfaces | `forest-900` dark, `paper` page, `bone` elevated and tinted, `ink-950` nav and footer |
| Action | `spring-500`, hover `spring-400`, pressed `spring-600`. The only filled action colour |
| Text | `fg`, `fg-2`, `body` on light; `bone`, `on-dark`, `on-dark-2` on dark. `muted` and `fg-3` are for non-text only: they do not reach 4.5:1 |
| Type | Bricolage Grotesque 700 for display, Public Sans 400 to 600 for everything read |
| Scale | `display-2xl` 80, `display-xl` 56, `display` 40, `heading-lg` 32, `heading` 24, `heading-sm` 20, `sub` 18, `body` 16, `body-sm` 14, `caption` 12. The top four are fluid |
| Radius | `xs` 8, `sm` 12, `md` 16, `lg` 24, `xl` 28, `2xl` 40, `pill` |
| Spacing | 4px steps below 24, 8px steps from 24. Sections use `--section-y` |
| Shadow | `nav` and `float`. Nothing else has one |

**Surfaces.** A section is `.s-light`, `.s-tint` or `.s-dark`. Each sets
`--card-bg` and `--card-line`, and cards read those, so a card never needs to
know which band it sits in.

**Buttons.** A pill (`.btn`, with `.btn-md` and `.btn-sm`) moves the visitor on.
The compact 8px `.btn-compact` is a control inside an interface.

**Cards** are flat: a surface and a hairline. A card that is a link answers the
cursor with its edge and its arrow. One that is not does nothing, so a response
always means there is somewhere to go.

**Tilted cards.** `.tilt` leans a card by `--tilt` (default 5 degrees, `.tilt-l`
for the other way) and gives it the floating shadow. A leaning card straightens
on hover and on keyboard focus. Text cards flatten below 700px; the photo fan on
the results page keeps its lean. Under reduced motion the lean stays, as a pose,
and stops animating.

**Navigation.** On desktop (1181px and up) the floating pill shows the link
row, with the jelly motion on the labels (`ui.js`). Scoliosis, Movement Training
(the mobility articles) and Pain Management (the injury articles) sit in a
small dropdown under Education that opens on hover or keyboard focus. Below that, the menu button
opens the card panel, after React Bits' CardNav: the pill grows downward and three
cards of grouped links drop in (Care, Learn, Clinic). The panel's markup comes from
`content/navcards.py` on every page, `ui.js` owns its state, focus and closing
rules, and `motion.js` animates it. With motion off it opens instantly.

**Spotlight.** Cards that are links or controls catch a soft light that follows the
pointer, after React Bits' SpotlightCard: service, article, route and library cards,
the consultation cards, the booking options (in the popup and on `book.html`), the menu cards and the dark
lead cards. The light reaches 80px past each card, so a grid shares one light, and it
swells when pressed. One controller in `ui.js` lights them all from a single loop that
stops when nothing moves; colours come from `--spot-*` properties in
`components.css`. Fine pointers only; under reduced motion the light snaps rather than
trails. Content cards (quotes, case studies, info cards) are left out on purpose.

**Empty photo wells.** Photography for the services and the articles has not
been shot. A small well inside a card collapses until it has an image, and a
large one becomes a forest panel with the clinic's Cobb-angle line drawing. The
art direction for each shot is still in the markup as a comment.

## Launch and backend handoff

The frontend is complete and honest about what it cannot do yet; the booking
and contact forms need a backend that another developer is building. This
section is the contract between the two. The full proposed architecture
(Nginx, Fastify/TypeScript, PostgreSQL, WhatsApp, Whish) is in
[`docs/backend-architecture.md`](docs/backend-architecture.md); where the two
differ, the field names and behaviors below are what the browser actually does.

**Existing** means built and verified in this repository. **Proposed** means
not built yet.

### Where things stand

| Area | State |
|---|---|
| Static site, generators, CI | Existing. GitHub Pages serves the staging copy. |
| Production hosting at `https://dr-rayhab.com` | Proposed. The domain did not resolve on 2026-10-15. |
| Booking UI, availability display, request states | Existing (frontend). |
| `GET /api/availability`, `POST /api/appointments` | Proposed (backend). |
| Contact form UI and states | Existing (frontend). |
| `POST /api/enquiries` | Proposed (backend). |
| Admin dashboard, payment selection, WhatsApp, Whish | Proposed; see `docs/backend-architecture.md`. |

Until the endpoints exist, every booking request and enquiry ends in an
honest "not sent" message with a WhatsApp (and, for enquiries, email)
fallback. Nothing is ever shown as sent unless the server confirms it.

### Configuration

| Setting | Where | Value |
|---|---|---|
| Production origin | `content/site_config.py` `SITE_URL` | `https://dr-rayhab.com` |
| API base | `content/site_config.py` `API_BASE`, written into every page as `<meta name="rayhab-api" content="/api">` | `/api` |
| Share image | `content/site_config.py` `SHARE_IMAGE` | `/assets/img/og/rayhab-share.jpg` (1200x630) |

The API base is a same-origin path on purpose: Nginx proxies `/api/` to the
backend, so no CORS is needed and no credentials or keys exist in the browser.
If the API ever moves to another origin, set `API_BASE` to the full URL,
rebuild, and add CORS for `https://dr-rayhab.com` only. There are no secrets in
the frontend and there must never be any: the browser is public.

### API contracts (what the frontend sends and expects)

All requests and responses are JSON. Times are Beirut local (`Asia/Beirut`).
The browser times out availability after 8 s and submissions after 15 s.

#### `GET /api/availability?service_id={id}&date={yyyy-mm-dd}`

Called by `site/assets/js/booking.js` when a day is shown.

- `service_id` is one of `assessment`, `follow`, `online`, `sports`, `pain`,
  `pain-follow` (the `TYPES` list in `booking.js`; keep the two in step).
- **200:**
  ```json
  { "date": "2026-10-20", "service_id": "assessment", "timezone": "Asia/Beirut",
    "slots": [ { "time": "09:00", "available": true },
               { "time": "10:00", "available": false } ] }
  ```
  The browser shows exactly these times, with unavailable ones disabled.
- Any other status, invalid JSON or a timeout: the browser falls back to the
  clinic's usual opening pattern (in `booking.js`) and tells the patient the
  time they pick is a request the clinic confirms.

#### `POST /api/appointments`

Sent when the patient presses **Confirm request** on step 4.

```json
{
  "service_id": "assessment", "for_whom": "me", "mode": "clinic",
  "date": "2026-10-20", "time": "09:00", "timezone": "Asia/Beirut",
  "first_name": "…", "last_name": "…", "email": "…", "phone": "…",
  "note": "…", "consent": true,
  "website": "", "elapsed_ms": 48210
}
```

`for_whom` is `me` or `child`; `mode` is `clinic` or `online`. `note` is
optional free text and may contain health information.

| Server response | What the patient sees |
|---|---|
| `200`/`201` with `{ "status": "requested", "id": "…" }` | "Booking request successfully sent" and the four next steps. **This is the only success.** |
| `422` with `{ "errors": { "first_name" \| "last_name" \| "email" \| "phone": "message" } }` | The messages under those fields on step 3, focus on the first. Other keys show a generic error. |
| `409` (slot no longer available) | Back to the time picker: "That time was just taken… your details will be kept." The day's availability is fetched again. |
| `429` | "Too many requests… wait a minute", with WhatsApp fallback. |
| `404`, `405`, `501` | Treated as "online booking requests aren't available right now", with WhatsApp fallback. |
| Any other status, network failure or timeout | A plain error with **Try again** and WhatsApp fallback. Entries are kept. |

The browser sends one request at a time and never retries on its own.

#### `POST /api/enquiries`

Sent by `site/assets/js/contact.js`.

```json
{ "first_name": "…", "last_name": "…", "email": "…", "phone": "…",
  "message": "…", "website": "", "elapsed_ms": 30512 }
```

`phone` is optional. Success is `200`/`201` with `{ "status": "received" }`;
the form then clears and shows a thank-you. `422` with `errors` keyed
`first_name`, `last_name`, `email`, `phone` or `message` puts each message
under its field. `429`, `404`/`405`/`501` and other failures behave as for
appointments, with WhatsApp and email offered.

### Server-side requirements (proposed)

The browser checks are for convenience only; the server must enforce:

- **Validation.** Names 2 to 80 characters; email well formed, at most 160;
  phone 8 to 15 digits after removing spaces, `+`, `(`, `)` and `-`; note and
  message at most 2000 characters; `consent` true for appointments;
  `service_id` from the catalog; `date` from tomorrow to 90 days ahead on an
  open day; `time` among the server's own available slots, re-checked inside
  the transaction that creates the request (`409` if gone).
- **Spam and abuse.** Reject (`400`, generic message, no detail) when
  `website` is not empty. Treat `elapsed_ms` under about 3000 as suspicious
  (flag, or require a further check). Rate-limit by IP (suggested 5 per
  minute, 20 per day for each endpoint) and by email and phone. Check the
  `Origin` header equals `https://dr-rayhab.com`. Add a challenge (such as
  Cloudflare Turnstile) only if abuse is observed; it would need a frontend
  change and a privacy-policy update.
- **Status discipline.** Return `{"status":"requested"}` only after the
  request is durably stored. A booking is `requested`, never confirmed, at
  this point.
- **Data.** Store the consent timestamp and the consent wording shown. Treat
  `note` and `message` as potentially health-related. No personal data in
  URLs, logs or analytics.

### Production hosting (Nginx, proposed)

The site is static: serve `site/` as built by CI, minus the staging step.

- **Do not run `content/staging_noindex.py` for production.** It exists only
  for the GitHub Pages mirror and would remove the site from search.
- **404:** `error_page 404 /404.html;` and make sure missing URLs return the
  404 status, not 200. `404.html` works at any depth because it sets its own
  `<base>`. (Verified on GitHub Pages: a missing URL returns 404 with this page.)
- **Redirects:** HTTP to HTTPS and `www` to the apex with a single 301 each.
  Also `301 /services/frc-joint-training.html` to
  `/services/joint-training-mobility.html` (the old URL is a noindex
  meta-refresh stub today).
- **Caching:** CSS and JS URLs carry a content hash (`?v=`), so
  `/assets/css/` and `/assets/js/` can be `Cache-Control: public,
  max-age=31536000, immutable`. Fonts likewise (they change only with a new
  file name). Images are not versioned: give them a week. HTML:
  `Cache-Control: no-cache`.
- **Compression:** gzip or brotli for HTML, CSS, JS, SVG, XML and JSON.
- **Security headers:** `Strict-Transport-Security` (after HTTPS is
  confirmed working), `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: strict-origin-when-cross-origin`,
  `Permissions-Policy: camera=(), microphone=(), geolocation=()`, and a
  Content-Security-Policy. The only inline scripts are the motion gate on
  every page and the base-path script on the 404 page, so scripts can be
  locked to hashes:

  ```text
  default-src 'self'; img-src 'self' data:; font-src 'self';
  style-src 'self' 'unsafe-inline'; connect-src 'self';
  script-src 'self' 'sha256-yb+kXgh5zw4DMCqxJK0NpZLXmcTGnfjGoW1XuTC6uLo=' 'sha256-48v3BVFceGGoCmEY8yhA3vVDPhB5xCDfXJYamli5VYQ=';
  base-uri 'self'; form-action 'self'; frame-ancestors 'none'; object-src 'none'
  ```

  `style-src` needs `'unsafe-inline'` for a few `style` attributes. If either
  inline script changes, its hash must be recomputed. Test the policy in
  report-only mode first.

### Analytics and consent

- **Existing:** none. No analytics, no tracking, no cookies, no browser
  storage, no third-party requests (fonts are self-hosted). No consent banner
  is needed today, and adding one would do nothing.
- **Proposed, only once a provider is approved:** count these events, with no
  names, emails, phone numbers, notes or messages in any payload or URL:
  `booking_request_sent` (only on a confirmed `requested`), `booking_request_failed`
  (with the error kind), `enquiry_sent`, and clicks on the primary booking
  buttons. A cookie-free provider avoids the need for consent; any provider
  that sets cookies or identifiers needs a working consent control first, and
  the privacy policy must name it.

### Acceptance checks for the backend

1. On staging, a booking request returns `{"status":"requested"}` and the
   patient sees "Booking request successfully sent"; the request exists in the
   database with its consent timestamp.
2. Two near-simultaneous requests for the same slot: one succeeds, the other
   gets `409` and is sent back to the time picker.
3. A `422` for an invalid email shows the server's message under the email
   field.
4. With the API stopped, the patient sees the "not sent" message, never the
   success screen.
5. A request with `website` filled is rejected and stored nowhere.
6. Rapid repeated requests from one IP are rate-limited (`429`).
7. The contact form succeeds only on `{"status":"received"}`.
8. `GET /api/availability` hides taken times, and they show disabled.
9. On production, a missing URL returns HTTP 404 with the branded page; HTTP
   and `www` redirect once to `https://dr-rayhab.com`; the headers above are
   present; `robots.txt` and `sitemap.xml` load; pages carry no noindex tag.

## Editorial conventions

These are load-bearing, not stylistic preferences:

- Where evidence is genuinely uncertain, articles say so in a dedicated
  "What is not settled" block rather than smoothing it over.
- No outcome is promised. Individual results vary, and the pages say so.
- Only measurements that exist are shown. One case study carries Cobb angles
  because an X-ray exists; the rest are labelled photographic.
- Unwritten content reads "In preparation" and does not link anywhere.
- No em dashes in anything written here: site copy, generator content and code
  comments all use a comma or a semicolon instead. The imported canvas and its
  runtime JavaScript still contain them, and are left byte-exact on purpose.
